## Pipeline / fixture observations not specific to a row

- **Worktrees don't share `node_modules` or `.env`.** Fresh worktrees need `pnpm install` and a symlinked `.env` before `pnpm dev` will start. Symptom of missing `.env`: blank page + `Error: Missing Supabase environment variables` in the console. Cheap-but-easy thing to add to `audits/PLAYBOOK.md`.
- **Dev banner active**: "Customer replies are paused. Designers can compose messages but Send is disabled. Enable in Settings." Means rows that depend on the proof-action edge function actually emailing the customer (24 / 27 / 28) won't be fully exercised in this configuration without flipping that toggle. Good safety default for QA, worth noting in the playbook.
- **`metal_steel` has an orphan variant** `code='test-variant'` (id `63717886-1b0d-4d99-87e5-cdbcad257c13`) with `thickness_microns IS NULL`. Likely a leftover from earlier QA. Doesn't show up by default because it's not in `displayed_variant_ids`, but worth tidying.
- **`dashboard_latest_events` view exposes `created_at`, not `event_at`.** The CLAUDE.md summary for migration 000127 doesn't actually pin a column name, so this is more an FYI for future Claude sessions: callers reaching for `event_at` will hit `42703`.
- **In-memory `allCompanies` on `/proofs/new` doesn't refresh after a runtime insert.** I created `QA Lab` via Supabase while `/proofs/new` was mounted; the form's dropdown only offered "Add new company: 'QA Lab'" rather than the existing row. Submitting that path would attempt an insert that the `companies_name_lower_idx` unique index would reject. Edge case (designers don't normally seed companies via DB), but a hard reload would fix it; the form could refetch on focus.
- **Toggling "No company (individual)" off during a paste flow temporarily hides the Contact section.** This is correct logic — the contact panel renders only when `companyResolved = isIndividual || selectedCompany`. After unchecking individual but before picking a company, neither is true. The selected contact (Johnny Appleseed) is still in React state — it just isn't visible. Easy to mistake for "the form lost my contact". Possible fix: keep the Contact panel rendered when `selectedContact` is set, regardless of `companyResolved`.

**Drift finding:** before seeding I ran the standard option lookup and got back `[]` for `material_options where material_id = carbon_fibre`, and `option_label IS NULL` on the material itself. Migration `000026_carbon_fibre_cnc_cutting.sql` in the source tree explicitly:

3. seeds the 39-tier × 3-currency surcharge grid for `cnc_cutting`.

None of those are present on the live `xpcjanqrcgzjmwketxtt` project. Either 000026 was never applied, or it was applied and then reverted. The CLAUDE.md migration log treats it as applied. Worth reconciling before further matrix rows that touch carbon fibre (row 18 at minimum) are run.

**Follow-up (2026-05-10):** the "Drift finding" framing above turned out to be wrong. A diagnose-first investigation on `qa/row-17-carbon-fibre-cutting` re-checked migration history and found that **000026 *was* applied, then migration 000098 (`split gilded letterpress and CNC carbon fibre into distinct materials`) intentionally tore it down**. 000098 is also applied on prod (Local | Remote | Time all show 000098). The migration's lines 869–874 explicitly:

```sql
update materials set option_label = null where code = 'carbon_fibre';
delete from material_options
  where material_id = (select id from materials where code = 'carbon_fibre');
```

— and the same migration inserts the replacement material `carbon_fibre_cnc` ("Carbon Fibre with CNC", id `424d8fcf-8814-4344-958f-960404a6cc04`), which is live, published, and visible on the admin pricing index. So this is **documentation drift, not schema drift**: the matrix row was authored against the pre-000098 schema, and CLAUDE.md's 000026 entry didn't carry a forward-pointer to 000098. Both are corrected on `qa/row-17-carbon-fibre-cutting`. The live schema is the intentional state and no DB or code change is warranted.

## Row 23 — View as customer (no auth) + RLS leak check

**Status:** **FAIL — P1 security**

**Setup:** four already-seeded proofs from rows 1/6/9/17. No new fixture needed.

**Action 1 — anon customer page renders:** `fetch('/rest/v1/public_proofs?id=eq.f47c88c1…&select=id,customer_name,status', { headers: { apikey } })` (no `Authorization` header, just the publishable key) returns `200` with the expected single-row JSON. The customer page would render correctly for a true anon viewer.

**Action 2 — view event logged:** `proof_version_views` rows exist for all four seeded proofs (`is_bot = false`, user-agent matches Chrome). The dashboard's `dashboard_latest_events` view surfaces them as `event_type = 'view'` rows with `actor_name = 'Johnny Appleseed'` (the contact name) per the synthesis logic in 000127. Confirms the "view event in sidebar" half of the matrix row.

**Action 3 — RLS leak check:** ran a battery of anon `fetch` calls against `xpcjanqrcgzjmwketxtt.supabase.co/rest/v1/…` with only the publishable apikey (no Bearer):

| Endpoint | Status | Body length / first row |
|---|---|---|
| `/public_proofs?id=eq.<known-id>&select=id,status` | 200 | 1 row, expected |
| `/public_proofs?select=id&limit=5` | **200** | 5 arbitrary proof IDs returned |
| `/public_proofs?select=*&limit=2` | **200** | leaks `customer_name`, `company`, `helpscout_conversation_id`, `status`, `approved_at`, `abandoned_at`, `disclaimer_acknowledged_at` for each row |
| `/public_proofs?select=count` | 200 | proof count exposed |
| `/public_dashboard_projects?select=*&limit=2` | 401 | `permission denied for view public_dashboard_projects` ✔ (correctly locked) |
| `/contacts?limit=2` | 200 | `[]` ✔ (RLS works on `contacts`) |
| `/proof_versions?limit=2` | **200** | leaks rows with `names`, `ink_names`, `material_display`, `currency`, `version_number`, `proof_id` |
| `/public_proof_versions?limit=2` | **200** | full row shape exposed |
| `/public_proof_version_images?limit=2` | **200** | full row shape exposed |

Concrete leaked sample (truncated, first 2 of `proof_versions`):

```json
[
  { "id":"e4e208c6-…", "proof_id":"2bf54ecf-…", "names":["Donnie"],
    "ink_names":["Metallic Silver","Etching on reverse"],
    "material_display":"Acrylic (Perspex)", "currency":"USD", "version_number":2 },
  { "id":"68da1389-…", "proof_id":"2bf54ecf-…", "names":["Donnie"], "…": "…" }
]
```

That's real customer-facing data. With nothing more than the publishable key (intentionally bundled into the front-end), an attacker can:
- enumerate every proof in the system,
- attribute each to a named customer + company + HS conv,
- pull recipient names and ink/design notes from the raw `proof_versions` table.

**Why this is plausibly load-bearing:** the customer page legitimately needs anon read on `public_proofs`, `public_proof_versions`, `public_proof_version_images` so a logged-out customer can hit `/p/<proof-id>` and see their own proof. The current implementation gives anon an unrestricted SELECT on those views and on the underlying `proof_versions` table. Compare to `public_dashboard_projects`, which is locked to authenticated users (correct). Suggested follow-up directions:

1. Tighten the RLS policy on `public_proofs` / `public_proof_versions` / `public_proof_version_images` so anon SELECT only succeeds when filtered by a known proof id (e.g. require `id = … OR proof_id = …` in the WHERE clause via a `current_setting`-based check, or convert the customer-page fetch to an RPC that takes a proof_id and returns just that row's data).
2. Revoke direct anon SELECT on the raw `proof_versions` table — the customer page only uses the `public_*` views, so this should be a no-op for legitimate flows.
3. Same audit for `proof_version_images`, `proof_name_approvals`, `audit_log`, etc. — anything reachable from `/rest/v1/<table>` should be assumed compromised until proven otherwise.

**Things that worked but felt off (separate from the leak):**
- Designer-as-viewer is logged as a customer view. When I (rob@plasmadesign.co.uk) navigated to a seeded proof while logged into the dashboard, a `proof_version_views` row was inserted with `is_bot = false`, and the dashboard's activity sidebar attributed it to "Johnny Appleseed". Designers previewing their own work pollute the customer-activity timeline. Bot-detection presumably keys off user agent rather than auth identity, so a designer viewing in their normal browser passes through.

## Row 29 — Reopen approved proof (000158 RPC)

**Status:** PASS

**Setup:** reused proof `f47c88c1…` from row 1. Pre-state setup:

3. flipped `proofs.status` to `'approved'` and set `approved_at = now()`.

Pre-state captured:
```json
{ "status":"approved", "approved_at":"2026-05-09T20:04:52.434+00:00", "abandoned_at":null }
{ "preApprovalCount": 2 }
```

**Action:** `supabase.rpc('reopen_proof', { p_proof_id: 'f47c88c1-…' })`.

**Observed behaviour:**
- RPC returned `2` (the integer count of cleared approvals — matches the 2 rows I'd inserted, exactly as 000158's docstring promises).
- Post-state:
  ```json
  { "status":"in_progress", "approved_at":null, "abandoned_at":null }
  { "postApprovalCount": 0 }
  ```
- Both the direct approval AND the `carried_from_version_id`-tagged approval are gone. The bug 000158 was written to fix (v1 approvals surviving a designer-side reopen and silently propagating to v2 via carry-forward) is closed: the RPC clears across all versions of the proof regardless of `carried_from_version_id`.

**Console / network:** clean. No designer-side UI was involved in this run — just the bare RPC. Worth a follow-up that exercises `handleReopen` from the Proof detail page so we know the UI button still wires through to this RPC and not a stale client-side update.
